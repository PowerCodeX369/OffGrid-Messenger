# Phase 2.0.2 — ESP32-C3 NimBLE setup and two-port flashing

## Why VS Code showed 11 errors

- `host/ble_hs.h`, `nimble/nimble_port.h`, and the other BLE headers belong to the **ESP-IDF `bt` component**, not to the OffGrid project. They become accessible when NimBLE is enabled in the **effective** project `sdkconfig` and the project has been configured.
- `mbedtls/md.h` belongs to the ESP-IDF `mbedtls` component.
- The supplied `main/CMakeLists.txt` already declares `REQUIRES bt mbedtls`; Phase 2.0.2 also checks that NimBLE is actually enabled. The C warning about `else` is fixed.
- VS Code's Microsoft C/C++ IntelliSense requires `build/compile_commands.json`. This is generated by ESP-IDF after **Reconfigure** or **Build**, not by the ZIP.

## Build steps (do in this order)

1. Open the **`firmware` folder itself**, not the parent `android` folder or the overall package root, in VS Code.
2. Command Palette -> `ESP-IDF: Set Espressif Device Target` -> `esp32c3`.
3. Command Palette -> `ESP-IDF: SDK Configuration Editor` -> `Component config > Bluetooth`:
   - `Bluetooth` enabled;
   - `NimBLE` as host stack (not Bluedroid);
   - `GATT server` and `Peripheral` role enabled.
4. Save. If you previously built the old firmware in the *same* folder, the existing `sdkconfig` can override `sdkconfig.defaults`. Re-check the actual settings in SDK Configuration Editor. When switching to a new extracted folder there is normally no old `sdkconfig`.
5. Open ESP-IDF Terminal, then run:

   ```bash
   idf.py set-target esp32c3
   idf.py reconfigure
   idf.py build
   ```

6. Verify `build/compile_commands.json` exists. If red squiggles remain but the build succeeds, run `ESP-IDF: Add VS Code Configuration Folder` and `ESP-IDF: Run idf.py reconfigure task`, then C/C++ -> Reset IntelliSense Database.

**Do not copy NimBLE headers into your project or manually add random include paths.**

## One command to build once and flash two boards

First identify physical devices on your Linux KDE laptop:

```bash
ls -l /dev/serial/by-id/ 2>/dev/null || true
ls -l /dev/ttyACM* /dev/ttyUSB* 2>/dev/null || true
```

Close Chromium/Web Serial and any serial monitors. Open an **ESP-IDF terminal** in the firmware project and run (substitute actual device paths):

```bash
python3 scripts/flash_both.py /dev/ttyACM0 /dev/ttyACM1
```

The script runs `idf.py build` **once** and then starts two *separate* esptool flashing processes concurrently using Espressif-generated flash arguments. It does not invoke two `idf.py` builds against the same build directory and does not erase NVS. Each board writes its own log to `build/offgrid_board_1_flash.log` and `build/offgrid_board_2_flash.log`.

If parallel flashing causes USB port conflicts, use the safe serial mode (still one command):

```bash
python3 scripts/flash_both.py /dev/ttyACM0 /dev/ttyACM1 --sequential
```

Alternatively VS Code: `Terminal > Run Task > OffGrid: Build + Flash BOTH ESP32s` (the task prompts for both ports). Depending on how VS Code was launched, a generic task terminal might not inherit `idf.py`; prefer the ESP-IDF Terminal command if it reports `idf.py` missing.

**Safety:** Verify both ports before flashing. Do **not** use `erase-flash`, `erase_flash`, or `fullclean` as a substitute for fixing header errors; erasing NVS destroys existing radio pairing keys. `fullclean` only removes the local build directory (but it is unnecessary for initial setup).

## Known validation limitation

This source package has been checked with local syntax/contract tests. It has not been compiled with a full ESP-IDF + NimBLE toolchain or physically flashed here. If `idf.py build` still fails, copy the first actual build error from the terminal (not only VS Code's Problems panel) so it can be fixed precisely.
